# 用户体系完善指南（低空综合服务平台）

本文结合当前仓库的实现现状（H5 + uni-app + Node/Express + 本地 JSON 持久化 + 管理后台）与前期沟通目标（统一客服信息、默认头像、RBAC 管理权限、可配置内容、Apple 风 UI），给出一套**可分阶段落地**的用户体系完善方案。

> 目标：让“登录—身份—权限—资料—订单/报名—后台管理”形成闭环，同时为后续迁移到 PostgreSQL 打好基础。

---

## 现状概览（你现在已经具备的能力）

- **后端**：`server/index.js`
  - 具备基础用户数据文件（`server/users.json`）与登录接口（`POST /api/login`）。
  - 具备管理员账号“兜底/修补”（`ensureAdminUsers`）。
  - 具备 CRUD 数据写入（申请单 `/api/submit`、列表 `/api/list`、服务配置 `/api/services/config` 等）。
- **前端（H5）**
  - 登录页、个人中心已完成默认头像替换与 Apple 风格改造。
  - 管理后台已具备：订单/用户管理、服务配置等能力。
  - 目前主要通过 `localStorage.setItem('user', ...)` 保存登录态。
- **前端（uni-app）**
  - 登录页存在模拟登录/微信登录示例逻辑（当前已将写死头像改为空字符串，走默认头像逻辑）。

---

## 当前用户体系主要问题（需要完善的点）

- **鉴权不完整**
  - 目前仅对 `/admin` 前端路由做了守卫，后端接口权限校验不够严格或未覆盖全量接口。
  - 使用 `localStorage` 保存 user 对象，缺少 token/会话机制，容易被伪造。
- **账号模型不清晰**
  - 账号字段目前既出现“手机号登录”，也出现“账号/密码登录”（例如后台管理员用账号字符串）。
  - 缺少“唯一标识规范”（手机号、用户名、openid、unionid 等）。
- **密码安全不足**
  - 若后端仍使用明文/弱加密，存在安全风险（需要 bcrypt/argon2）。
- **用户资料缺失**
  - 缺少完善的个人资料编辑：昵称、头像、手机号绑定、单位/学校、实名认证状态等。
  - 默认头像、头像上传、头像裁切/预览的体验还可继续统一。
- **权限体系需要产品化**
  - 目前有 `admin` / `dsl_admin` / `user` 等角色，但缺少“权限点/资源范围”的定义与审计。
- **数据存储与可扩展性**
  - JSON 文件适合早期，但并发、审计、查询、事务、备份/恢复能力不足。
  - 后续若要上 PostgreSQL：需要迁移策略和表结构规划。

## 目标用户体系（建议的产品与技术形态）

### 1) 账号体系（Identity）
建议统一支持三类登录方式，按阶段逐步上线：

- **手机号 + 密码**（基础）
- **手机号 + 验证码**（更符合 C 端习惯）
- **微信登录**（uni-app/小程序场景）：openid/unionid 绑定用户

推荐确定以下规范：

- **userId**：UUID 或雪花 ID（不要再用随意字符串拼接）
- **loginId**：
  - 手机号登录：`phone`
  - 管理员账号：`username`（不建议继续把它放到 phone 字段）
  - 微信登录：`wechatOpenId`（可选 unionid）

### 2) 鉴权（Auth）
推荐使用 **JWT Access Token + Refresh Token**：

- **Access Token**：短期（如 30min），用于请求接口
- **Refresh Token**：长期（如 7~30 天），用于续签
- **存储位置**
  - H5：优先 `httpOnly` cookie（更安全），或 localStorage（需防 XSS）
  - uni-app：`uni.setStorageSync`

后端需要统一中间件：

- `authRequired`：校验 token，挂载 `req.user`
- `roleRequired(['admin', 'dsl_admin'])`：RBAC 校验

### 3) 权限模型（RBAC + Scope）
建议分两层：

- **角色（Role）**：`user`、`admin`、`dsl_admin`
- **权限点（Permission）**：如
  - `service_config:read/write`
  - `orders:read/write`
  - `users:read/write`
  - `upload:write`

并增加“资源范围”：

- `dsl_admin` 仅能看到/处理 **赛事(13)** 或某些服务范围的订单
- `admin` 拥有全量权限

### 4) 用户资料（Profile）
建议拆出用户资料与状态字段：

- 基础：`name`、`avatar`、`phone`、`email`
- 业务：`company/school`、`role`、`isVerified`、`verifiedAt`
- 追踪：`createdAt`、`lastLoginAt`、`lastLoginIp`

并提供：

- **头像上传接口**（复用现有 `/api/upload`），但要增加：
  - 文件类型白名单、大小限制
  - 上传鉴权（至少登录后才允许上传头像）

## API 设计建议（后端）

> 下面是建议的接口集合，可按阶段实施；保留你现有接口不动，逐步替换前端调用。

### 1) 登录/会话
- `POST /api/auth/login`（手机号+密码 / 用户名+密码）
- `POST /api/auth/login-sms`（手机号+验证码）
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `GET  /api/auth/me`（获取当前登录用户）

### 2) 用户资料
- `PATCH /api/users/me`（修改昵称、头像等）
- `POST  /api/users/me/avatar`（上传头像，可选）

### 3) 管理员（RBAC）
- `GET /api/admin/users`
- `PATCH /api/admin/users/:id/role`
- `GET /api/admin/orders`（支持 serviceId、status、dateRange、keyword）
- `PATCH /api/admin/orders/:id/status`

### 4) 安全与治理
- 登录接口加 **限流**（IP + 账号维度）
- 关键操作写 **审计日志**（谁在什么时候改了谁的角色/改了哪条订单）

## 前端改造建议（H5 + uni-app）

### 1) 统一登录态存储与获取
- 建议封装 `authStore`（Pinia / uni-app store）
  - `user`
  - `accessToken`
  - `refreshToken`
  - `isAuthed`
  - `login() / logout() / refresh() / fetchMe()`

### 2) Axios 拦截器（H5）
- 请求：自动带 `Authorization: Bearer <token>`
- 响应：401 自动触发 refresh；refresh 失败则跳转 `/login`

### 3) 路由守卫（H5）
- `meta.requiresAuth`
- `meta.requiresRole`
- 对 `/admin`：既做前端 guard，也要后端接口校验（前端 guard 只能提升体验，不是安全边界）

### 4) 默认头像策略（统一）
- **后端**：`avatar` 空字符串代表“未设置头像”
- **前端**：统一用同一个默认占位（你现在 H5 已实现，uni-app 也建议对齐）

## 数据存储：继续 JSON 还是迁移 PostgreSQL？

### 继续 JSON（短期可行）
适合：单机、低并发、快速迭代。

要补强：
- 写入加锁（避免并发写文件导致数据损坏）
- 备份策略（定时备份 `*.json`）
- 日志与审计（单独文件落盘）

### 迁移 PostgreSQL（中长期推荐）
优点：
- 并发与一致性更好（事务）
- 查询能力强（筛选订单/用户/统计）
- 审计、权限、报表更容易做

成本说明（结合前期沟通）：
- **PostgreSQL 软件本身免费开源**；
- 若使用云托管（RDS 等）会产生实例/存储/流量费用；
- 自建只算机器与运维成本。

## 推荐实施路线图（最小可用 → 稳健安全 → 可扩展）

### Phase 0：收口规范（1-2 天）
- 明确账号字段：手机号/用户名不要混用
- 默认头像策略统一（已基本完成）
- 服务端补齐“后端权限校验”中间件框架

### Phase 1：Token 鉴权 + /me（2-4 天）
- 上线 `/api/auth/login`、`/api/auth/me`
- 前端接入 token + axios 拦截器
- 后端对敏感接口加 `authRequired`

### Phase 2：RBAC 产品化（2-4 天）
- `roleRequired` 覆盖：服务配置、用户管理、订单状态修改
- `dsl_admin` 增加 scope（只看 serviceId=13 或指定范围）

### Phase 3：资料完善与安全治理（3-7 天）
- 个人资料编辑（昵称/头像/绑定手机号）
- 登录限流、密码强度、审计日志
- 数据备份与恢复演练

### Phase 4：迁移 PostgreSQL（按上线节奏）
- 设计表结构（users / orders / service_configs / audit_logs）
- 编写一次性迁移脚本（json → pg）
- 双写/灰度切换（可选）

## 验收清单（完成用户体系后的“能用/安全/可运营”标准）

- **能用**
  - 用户可注册/登录/退出
  - 个人中心展示与编辑资料
  - 研学/培训等报名数据可追溯到用户
- **安全**
  - 密码加密存储
  - 后端接口权限严格校验
  - 登录限流 + 关键操作审计
- **可运营**
  - 后台可按角色/服务范围查看订单
  - 用户列表、角色变更可控
  - 服务配置修改有记录、可回滚
