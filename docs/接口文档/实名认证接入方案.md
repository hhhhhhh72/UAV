# 实名认证接入方案

> 状态：方案待评审（评审后进入开发排期）
> 范围：一期 身份证二要素核验；二期 人脸核身（强实名）；三期 数据应用（门槛/风控）
> 关联模块：实名认证页 `miniprogram/pages/mine/auth.vue`、飞手认证 `pkg-talent/pages/pilots/apply.vue`、用户表/认证数据

---

## 一、背景与目标

### 现状
- 「实名认证」页（`pages/mine/auth.vue`）展示的是**飞手认证申请**结果：姓名 + 身份证号仅填表存储（已 AES 加密），**无真实性核验**——造假证号也可提交通过人工审核。
- 平台尚未接入任何第三方身份核验服务。

### 目标
1. **堵住假证号**：提交即核验，姓名与身份证号必须真实且匹配；
2. **为强实名铺路**：飞手认证、会员体系、发布需求/接单等业务可复用同一核验结果；
3. 数据合规：仅在用户明确授权下收集，加密存储、脱敏展示、日志无明文。

### 一期/二期边界

| 期 | 内容 | 单次成本（约） | 上线时间 |
|---|---|---|---|
| 一期 | 身份证**二要素**核验（姓名 + 证号） | 0.1~0.5 元/次 | 本方案评审后 3~5 天 |
| 二期 | 证件 OCR（拍照自动填）+ **人脸核身**（人证合一） | OCR 0.1~0.3 元/次；人脸约 1 元/次 | 一期稳定后 |
| 三期 | 实名结果作为业务门槛（飞手申请/发布/接单） | — | 待产品决策 |

## 二、服务商选型

| 候选 | 类型 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **阿里云云市场**（身份证二要素） | 二要素 | 企业资质即可开通、按次计费、稳定、文档全 | 商品由第三方入驻，质量需选好评商家 | **一期推荐** |
| 腾讯云市场 / FaceID | 二要素/三要素/人脸 | 云厂商一条龙，人脸核身成熟 | 二要素单价略高 | **二期做人脸推荐** |
| 聚合类平台（聚合数据等） | 二要素 | 便宜 | 数据源质量参差，合规敏感场景慎用 | 不推荐 |
| uni 实人认证（DCloud） | 人脸 | DCloud 官方 | 绑定 uniCloud，本项目未使用 | 不适用 |
| 微信官方 | 手机号快速验证 | 免费、官方 | 仅证明手机号归属，**不等同身份证实名** | 可作为补充 |

**决策要点**：均要求**企业主体**（营业执照 + 对公验证），个人主体不可开通——用公司主体注册阿里云账号并完成企业认证即可。

## 三、总体流程与架构

```
小程序实名页 ──POST /api/v1/realname/verify──► Go 后端
  │  填姓名 + 证号                                │ ① 参数校验（证号校验位/长度、姓名规则）
  │                                               │ ② 用户鉴权 + 限频（5 次/10 分钟，与短信防爆破一致）
  │                                               │ ③ 调第三方核验（服务商 Key 仅存后端 .env）
  │                                               │ ④ 结果映射 + 加密存储（AES-256-GCM）
  │                                               │ ⑤ 审计日志（不含明文身份信息）
  │◄───────── { status, masked_id, ... } ─────────│
```

- **密钥安全**：服务商 AppCode/Secret 放服务器 `.env`（`ALIYUN_REALNAME_APPCODE` 等），compose 从 `.env` 注入（沿用现行为约定），**严禁入库**；
- **分层铁律**：Handler（解析/调用/响应）→ Service（校验/状态机/调仓库）→ Repository（加密落库）；第三方调用封装为可注入的 `Provider` 接口（生产走 HTTP 实现，测试用 mock），不破坏现有分层；返回/失败统一走 `respond/fail`；
- **失败策略（fail-closed）**：核验服务不可用时，实名请求判为"暂不可用"，**绝不放行**；用户侧提示"核验服务暂时不可用，请稍后再试"；
- **缓存**：同一用户核验通过的结果缓存 24h（防重复计费）；失败（不匹配）不缓存，允许重试（受限频约束）。

## 四、接口契约（一期）

### 1. 提交核验

`POST /api/v1/realname/verify`（需登录）

请求：

```json
{
  "real_name": "张三",
  "id_number": "500101199001011234"
}
```

服务端校验：
- 姓名：2~30 字符（汉字/少数民族名字允许空格与 ·）；
- 证号：18 位，**校验位算法（GB 11643）本地预校验**，不合法直接 400，不消耗第三方调用；
- 限频：同一用户 5 次/10 分钟（429）。

响应（200）：

```json
{
  "status": "verified",            // verified | mismatch | unavailable
  "masked_id": "5001**********1234",
  "verified_at": "2026-08-31T10:00:00+08:00"
}
```

错误码：`400` 参数非法 / `401` 未登录 / `429` 频率超限 / `502` 第三方服务不可用。

### 2. 查询当前实名状态

`GET /api/v1/realname/me`（需登录）→ 返回脱敏信息与状态（供实名页/业务门槛复用）。

### 3. 数据存储

- 新增表 `realname_verifications`：`user_id`、`real_name_enc`（AES 加密）、`id_number_enc`（AES 加密，仅飞手/强实名场景需要完整号时保留）、`masked_id`、`provider`、`status`、`verified_at`、`created_at`；
- **最小化原则**：一般核验通过后**仅存脱敏号 + 核验结果**；完整证号仅在确需（如证书/强实名档案）时加密存储并在隐私政策中声明用途；
- 页面展示一律走 `mask` 工具（已有 `frontend/src/utils/mask.js` 同款逻辑，小程序侧沿用现有脱敏函数）。

## 五、前端改造（一期）

`miniprogram/pages/mine/auth.vue`：

1. 保留现有飞手认证信息展示；
2. 增加「身份核验」区块：姓名 + 证号输入 → 提交按钮 → 调 `/api/v1/realname/verify`；
3. 结果态：核验通过（✅ 状态）+ 核验失败（提示"姓名与证件号不匹配，请核对"）+ 服务不可用（"请稍后再试"）；
4. 提交前展示**授权文案**：明确告知用于身份核验、存储方式与用途；
5. 防误触：提交后按钮 loading，成功前不允许重复提交（与限频双保险）。

## 六、合规要点

1. **授权**：收集姓名、身份证号前必须获得用户明确授权（勾选协议/弹窗声明）；
2. **最小化**：不存不必要的完整证号；展示一律脱敏；
3. **加密**：存储沿用 `ENCRYPTION_KEY`（AES-256-GCM）加密；传输走 HTTPS；
4. **日志**：核验请求/结果日志不允许出现姓名、证号明文（logger 现有脱敏约定沿用，新增字段同样禁止）；
5. **删除权**：用户注销（未来功能）时同步删除核验记录。

## 十、风险与应对

| 风险 | 应对 |
|---|---|
| 第三方涨价/服务停摆 | Provider 接口抽象，二期预留切换（腾讯云/阿里云均可）；fail-closed 保底 |
| 恶意刷核验（费用消耗） | 限频 5 次/10min/用户 + 401 未登录不可核 + 监控单用户当日调用量 |
| 假证件兜底（二要素绕过） | 二要素仅校验真实性/匹配度；**人脸核身（二期）**才是强实名终局方案 |
| 合规风险（个人信息） | 授权文案、最小化存储、加密、日志脱敏、删除权（本章节第六节逐条落实） |
