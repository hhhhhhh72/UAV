## 一、方案优点

1. **行业定位清晰**：「资源连接器、供需撮合器、产业服务窗口、产学研转化枢纽、行业合规服务中心」五个定位与七大系统一一对应。
2. **场景覆盖完整**：制造 / 运营 / 科研 / 院校 / 通航场地 / 应急全产业链均有覆盖。
3. **「平台作用」逐条对齐协会落地价值**，适合直接进 PPT 建设方案。
4. **边界声明明确**：「不替代政府监管平台，不开展飞行计划审批、空域管控等行政执法职能」——规避职能冲突的意识正确。

---

## 二、问题清单

### P0 — 功能归属交叉重叠（实现冲突的源头）

方案未给任何功能划定**唯一权威归属**，同一功能在多个系统中出现：

| 功能 | 方案出现位置 | 后果 |
|---|---|---|
| **培训** | ② 供给能力展示大厅（"…检测标定、培训、空域协调服务"）+ ⑤ 培训课程超市 | **已实锤**：开发中出现两个培训入口（金刚区 vs 供给大厅），最终回滚②，培训归⑤ |
| **场地 / 试飞** | ① 场地资源台账 + ② "试飞测试"供给 + ③ 中试基地资源预约入口 | 同一资源三处出现，未定义数据由谁维护、预约入口以谁为准 |
| **应急调度** | ② 场景资源集市（"应急救援资源调度库"）+ ⑦ 应急资源协同调度 | ② 已覆盖⑦ 的核心功能，⑦ 名存实虚 |
| **院校对接** | ③ "搭建企业与海联职院、各大研究院常态化线上对接通道" + ⑤ 校企共建订单班/实训基地意向对接 | 重复 |

**修改原则**：每个功能在方案中只出现一次；确需跨系统引用的，必须注明「入口承接至 X 系统」。

### P1 — 定位与职能边界模糊

- **「行业舆情研判」（系统四）**：归集低空事故舆论、提供舆论应对参考——近似政府舆情/媒体职能，与「市场化产业生态服务载体」定位相悖；对 180 家会员属低频价值、维护成本高。建议移除，或降级为会员可选增值服务。
- **「供需撮合」定位为核心商业化功能，但全文无商业化设计**：撮合后的交易机制、付费模式（会员费/佣金/广告）、平台收益模型均未涉及。方案只有功能罗列，没有商业闭环。

### P1 — 三套术语体系互不兼容

| 术语体系 | 来源 | 示例 |
|---|---|---|
| 产业分类 | 系统一 会员档案库 | 整机 / 零部件 / 飞控 / 载荷 / 运营服务 / 实训院校 / 通航机场 / 检测机构 |
| 需求类型 | 系统二 需求发布大厅 | 巡检 / 测绘 / 应急 / 农林植保 / 低空文旅 / 设备采购 / 技术开发 |
| 供给类型 | 系统二 供给展示大厅 | 整机 / 零部件 / 航拍服务 / 试飞测试 / 检测标定 / 培训 / 空域协调 |

三套名称互不兼容，直接导致代码中出现三套独立枚举（`demand.BizType` / `ProductType` / 企业注册分类）。**建议方案层先统一一套「业务类型」标准，各系统引用同一标准。**

### P2 — 其他

- 系统七命名为「低空应急资源协同调度**模块**」，与前六个「系统/子系统」命名不齐。
- 缺 **MVP 分期与优先级**：面向 180 家会员的平台，七大系统全部建设的工作量与上线顺序未规划。
- 缺 **运营机制**：供给数据由谁上架、真实性如何保证、审核流程是什么（当前实现为管理后台手工上架）。
- 「企业案例库」在方案中未单列（仅系统六会员宣传专区提及"案例"），但代码已实现 `case_entries` 模块——方案遗漏或归属不清。

## 三、修正建议（对照当前实现状态）

| 方案条目 | 建议归属 | 当前代码状态 |
|---|---|---|
| 培训 | ⑤ 培训课程超市（唯一入口） | ✅ 已按修正后形态实现：金刚区「考证培训」→ `pages/training/courses`，供给大厅无培训 |
| 供给大厅 | ② 专责：整机 / 零部件 / 航拍服务 / 试飞测试 / 检测标定 / 空域协调 6 类 | ✅ 已实现：服务页三分区（设备 / 服务 / 场地） |
| 应急调度 | ⑦ 专责（② 场景资源集市仅保留「资源池」概念） | ✅ 已实现：`emergency-dispatches` 归⑦ |
| 场地资源 | ① 建台账、③ 承接预约入口、② 仅做展示卡片 | 🟡 当前 `test_sites` 单模块承载，三处未打通 |
| 术语统一 | 方案层制定统一业务类型标准 | ❌ 未开始（代码三套枚举） |
| 舆情研判 | 建议移除或降级 | ❌ 未实现（未动工，恰好无返工成本） |
| 商业化设计 | 方案补一章：交易机制 / 付费模式 / 收益模型 | ❌ 未实现 |

---

## 四、结论

方案作为商务汇报材料质量高，但作为**开发输入**需要一次「归属对齐」修订：以本评审为底稿，逐条确定功能的唯一归属（或入口承接关系），统一业务类型术语，再补充 MVP 分期与商业化设计。修订可在原 `.doc` 上直接进行，或另出修订版文档。

> 注：当前代码形态恰好已是「修正后方案」的形态（培训唯一入口、应急归⑦、供给大厅 6 类）——本轮评审最核心的冲突已在开发中消除。
