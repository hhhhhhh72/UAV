# 资金闭环与真实支付接入设计

> 状态：一期（平台内部记账 + 商城订单资金闭环）已上线；二期（微信支付真实资金）已预留接口与对账口径，等商户号到位即可接。
> 本文只写代码里真实成立的规则，凡是还没做的一律标注。

## 一、一句话现状

平台有一套内部托管金账本（`escrow_accounts` 余额/冻结 + `escrow_transactions` 流水），
商城订单、培训报名都已接入：下单不动钱，付款冻结买家余额，确认收货把钱放给卖家，取消/售后退回买家。
这些钱目前全部是平台自己记出来的（`channel = internal*`），没有一分真实资金进入平台账户；
真实资金的入口（微信支付）只留了位置：渠道字段、外部支付单号、回调幂等、按渠道对账。

## 二、账本模型

| 表 | 作用 | 关键列 |
|---|---|---|
| `escrow_accounts` | 每个用户一行：可用余额 + 冻结金额 | `user_id` / `balance_fen` / `frozen_fen` |
| `escrow_transactions` | 每一笔资金动作的流水（唯一真相） | `tx_type` / `amount_fen` / `reference_type` / `reference_id` / `channel` / `external_txn_id` |

`tx_type` 五种，语义固定：

| tx_type | 含义 | 余额影响 |
|---|---|---|
| `deposit` | 入金（内部记账或真实支付到账） | 目标用户 balance +amount |
| `freeze` | 资金进入托管（下单付款 / 报名缴费） | 付款方 balance -amount、frozen +amount |
| `release` | 放款给收款方（确认收货 / 结课） | 付款方 frozen -amount、收款方 balance +amount |
| `refund` | 退回付款方（取消订单 / 售后退款） | 付款方 frozen -amount、balance +amount |
| `transfer` | 余额内转账（已放款后的售后退款） | 卖家 balance -amount、买家 balance +amount |

原子性：余额调整与流水写入在同一事务/同一临界区内完成，全成或全败；
余额不足返回 `ErrInsufficientBalance`、冻结不足返回 `ErrInsufficientFrozenBalance`，由上层映射成业务错误。

## 三、渠道（channel）：分清真钱和平台记的账

| channel | 谁写入 | 有真实资金吗 | 有外部单号吗 |
|---|---|---|---|
| `internal` | 平台内部业务记账（默认值） | 无 | 无 |
| `internal_self` | 用户自助充值（小程序我的钱包→充值，模拟通道） | 无 | 无 |
| `internal_admin` | 管理员代充（线下对公转账/现金收款后补记） | 无 | 无 |
| `wechat` | 微信支付回调（服务端，签名校验后入账） | 有 | 必填 `transaction_id` |

规则（`domain.IsRealChannel`）：不是 `internal` 前缀的渠道一律当真实资金处理——
真实渠道入账必须带外部支付单号，否则直接拒绝：没有凭证就没有钱，绝不允许凭空多出一笔余额。

渠道由服务端判定，前端传什么都不采信：

- 用户调 `POST /api/v1/escrow/deposit` → `internal_self`
- 管理员调同一接口（可带 `to_user` 代充）→ `internal_admin`
- `wechat` 只能由支付回调写入，任何登录用户都无法自己造一笔微信已收款的余额

## 四、商城订单的四条资金流（一期已实现）

| 动作 | 触发 | 资金动作 | 幂等键 |
|---|---|---|---|
| 下单 | `POST /api/v1/trade-orders` | 不动钱（只是状态 `pending`） | — |
| 付款 | `POST /api/v1/trade-orders/{id}/pay` | 冻结买家 `amount_fen`；余额不足 → 402 引导充值 | `HasFrozen(buyer, trade_order, order_id)` |
| 发货 | `PATCH .../status` → `shipped` | 不动钱（仅卖家可置） | — |
| 确认收货 | `PATCH .../status` → `completed`（仅买家，须先 `shipped`） | 解冻买家、入账卖家 | `Release` 内部按 `(buyer, trade_order, order_id)` 查重 |
| 取消 | `PATCH .../status` → `cancelled`（仅 `pending`/`paid`/`shipped`） | 解冻退回买家，并把商品恢复为 `listed` | `HasRefunded` |
| 售后退款 | `POST .../aftersale` + `.../aftersale/review` 同意 | 见下 | `HasFrozen` / `HasReleased` 判定分支 |

售后同意后的三种情形（`TradeOrderService.refundForAftersale`）：

1. 货款还在冻结里（订单 `paid`/`shipped`）：从冻结退售后金额给买家，剩余部分放给卖家（部分退款＝双方降价成交）。
2. 货款已放给卖家（订单 `completed`）：从卖家余额扣回给买家（`transfer`）；卖家余额不足则审批失败、状态保持待审核可重试，绝不静默吞掉。
3. 这笔订单从没冻结过钱（老数据 / 管理端直接建单）：没有钱可动，记 Warn 日志后按状态结案，不产生任何退款流水。

售后被驳回：订单状态恢复到申请前的状态（`aftersale_from` 字段），买家可以重新申请——
此前驳回一律置 `completed`，导致已付款未发货的订单卖家再也发不了货。

赔付与人工介入：状态落定后资金动作失败（例如卖家余额不足）会记 Error 日志并返回错误，
钱始终留在托管里，最坏是延迟到账，不会丢；由运营人工处理后重试（各资金动作都幂等）。

## 五、真实资金接入（微信支付）：已就位与待办

### 5.1 代码里已经就位的（本次交付，已通过测试）

- `escrow_transactions.channel` / `external_txn_id` 两列（迁移 `000104`），历史数据默认 `internal` / 空串。
- 唯一索引 `idx_escrow_external(channel, external_txn_id) WHERE external_txn_id <> ''`：同一笔外部支付只能入账一次。
- `EscrowService.DepositFromChannel(ctx, userID, amountFen, channel, externalTxnID)`：所有入金的唯一入口，返回 `created` 表示本次是否真的加了钱。
  - 真实渠道缺外部单号 → 拒绝；
  - 同一 `(channel, external_txn_id)` 重复调用 → 返回原流水、不再加钱（微信回调会重试，这是防印钞的关键）；
  - 并发回调 → 唯一索引挡住第二次写入，服务自动重查并按幂等成功返回。
- `EscrowService.Reconcile(ctx, channel, from, to, limit)` 与 `GET /api/v1/admin/escrow/reconciliation?channel=&from=&to=&limit=`：按渠道汇总入金笔数/金额 + 逐笔明细，仅平台管理员可见。
  - `channel` 默认 `internal`，传 `all` 表示不限渠道；
  - `from`/`to` 支持 `RFC3339` 或 `2026-09-11` 日期（日期按自然日，含当天全天，左闭右开）；格式错误返回 400。
- 配置项（`internal/config`）：`WECHAT_PAY_MCHID` / `WECHAT_PAY_API_V3_KEY` / `WECHAT_PAY_CERT_SERIAL` / `WECHAT_PAY_PRIVATE_KEY_PATH` / `WECHAT_PAY_NOTIFY_URL`。
  五项必须齐全或全部留空，半配置直接启动失败；生产环境回调地址必须是 https。启动日志会打印商户号（密钥与序列号脱敏）。

### 5.2 待办（等微信商户号到位后按顺序做）

1. 发起支付：`POST /api/v1/payments/recharge`（登录用户）→ 生成平台订单号 `out_trade_no`（建议 `RC` + 日期 + 序列，落 `recharge_orders` 表）
   → 调微信 `POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi`（小程序 JSAPI 下单）→ 返回 `prepay_id` 与前端支付参数。
2. 回调入账：`POST /api/v1/payments/wechat/notify`（公网、免鉴权、必须 https）
   - 验签：`Wechatpay-Signature` 用微信支付平台证书/公钥做 RSA-SHA256 验签，验不过一律 401 且不入账；
   - 解密：`resource` 用 APIv3 密钥 AES-256-GCM 解密，取 `out_trade_no` / `transaction_id` / `amount.total` / `trade_state`；
   - 校验：金额必须等于 `recharge_orders.amount_fen`（防篡改），`trade_state` 必须为 `SUCCESS`；
   - 入账：`escrow.DepositFromChannel(ctx, userID, amount, domain.ChannelWeChat, transaction_id)`；
   - 应答：成功返回 `{"code":"SUCCESS"}`，失败返回 4xx/5xx 让微信重试（重试是幂等的，不会重复加钱）。
3. 真实退款：走微信 `POST /v3/refund/domestic/refunds`，`out_refund_no` 用售后单号；
   退款回调成功后再动平台账本（先外部后内部，避免平台退了微信没退）。
4. 提现／出款（当前完全没有）：用户余额目前只能用于平台内消费，无法提现。
   要做真实资金闭环必须补：提现申请 → 风控/人工审核 → 微信商家转账或银行卡代付 → 结果回调 → 记账（新增 `tx_type=withdraw`）。
   在提现通道打通前，`internal_*` 产生的余额不得视为可提现余额。
5. 每日对账：拉微信账单（`GET /v3/bill/tradebill`）与 `escrow_transactions` 按 `external_txn_id` 逐笔核对，差异进人工工单。
6. 管理后台补一个资金对账页面（渠道筛选 + 日期区间 + 入金合计 + 明细导出）；接口已就绪。

## 七、历史遗留与已知问题

- 生产库里存在测试性质的订单与余额（含亿元级测试单），`channel` 均为 `internal*`，可用渠道字段一眼区分；
  真实资金上线前建议清理，避免成交额与对账口径被污染。
- 交易额统计目前等于订单 `amount_fen` 求和（含测试数据）；接真实支付后应改为按 `channel=wechat` 的 `deposit`/`release` 汇总。
- 卖家可以审核自己订单的售后（自审自批），一期保留（便于小规模运营），二期建议改为平台仲裁。
- 管理员可以取消 `shipped` 状态的订单（会退款给买家），是否符合业务需产品确认。
- 用户自助充值（`internal_self`）单笔上限 20 万元，且可在小程序反复调用：它只会产生平台内部余额，
  在提现通道打通前不构成直接资金损失，但接真实支付后应逐步下线该入口，改为发起真实支付。
